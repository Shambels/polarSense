Seeing the data, not just its columns

Part 01

The question underneath all three features

Expand, details and graph look like three rendering features. They are not. Each needs data that the thing on screen does not contain.

What a notebook prints for a polars frame is a text/html table that polars has already truncated — ten rows, first and last columns, an ellipsis in the middle. The rows you want to page to were never sent. So a renderer that receives that output cannot paginate it, cannot compute a null count, and cannot plot a distribution. It has the ellipsis, not the data behind it.

Which means the real question is not "can a VS Code extension draw a nicer table" — obviously it can — but where does it go to get row 5,000. There are exactly two answers, and they are different products.

A · From the file what v1 already does

PolarSense already resolves the frame under the cursor to a concrete parquet, CSV, Arrow IPC, Delta or Iceberg file, and already ships hyparquet, whose reader takes rowStart and rowEnd and a column subset. Page 2 is one more range read of a file whose footer is already in the cache.

  • No Python, no kernel, no interpreter
  • Identical in .py and .ipynb — same resolver, same code path
  • Works before the code has ever been run
  • Zero new dependencies
  • Shows the source, not the result of a filter or join
  • A frame built in memory has no file to read

B · From the kernel new trust model

The Jupyter extension exports a stable Kernels API through @vscode/jupyter-extension: kernels.getKernel(uri) then kernel.executeCode(code, token), an async iterable of outputs that runs without touching the execution count or history. This is the PyCharm experience exactly.

  • The real frame, after every transform
  • Works on frames with no file behind them at all
  • Only kernels the user has already started, in an open notebook
  • Per-extension consent prompt; revocable via Jupyter: Manage Access To Jupyter Kernels
  • Means PolarSense executes Python in your session
  • Nothing for a plain .py run in a terminal
The pick

A first, B second, and never A replaced by B. Path A is v1 with a webview on the end — the resolver, the schema cache and the parquet reader are all already written and already tested. Path B is a genuinely new extension with a genuinely new promise to the user. Shipping A alone covers the common case, which is a script that reads a file and prints the frame; and it covers it in .py files, where path B has nothing to offer at all.

The honest gap in A

For df.filter(pl.col("region") == "EU").collect(), the file-backed viewer shows you the whole file, not the 400 rows that survived the filter. That is a real difference from what PyCharm shows and it should be said on the panel itself — a header reading source file · 4.2M rows · filters not applied is honest; silently showing 4.2M rows and calling it the frame is not. Closing that gap is path B, and it is the entire reason path B is on this roadmap rather than dismissed.

Part 02

The three features, one at a time

All three are feasible. They are not equally feasible, and the order below is the order of increasing cost, which is also the order they should be built in.

Show details shipped src/preview/details.ts · polarsense.showDetails

It was the cheapest of the three, and for the reason predicted: the data was already read. Dtype, null count, min and max per column come out of the parquet footer the completions had already paid for, and the panel is that content with a row per column instead of a tooltip for one. Row count, row-group count, file size and codec came out of the same footer — the row groups and the codec fold into the statistics walk that was already there, and the file size is the stat the cache key needed anyway.

Distinct-count and a real describe() stayed out, as planned. What the plan did not spell out is what a footer-only panel does with a CSV: rather than a grid of blanks, the statistics columns are dropped entirely when nothing in the file recorded any, and a statistic the writer left out prints an em dash rather than a zero — "no nulls" and "the writer did not say" are different answers.

The panel calls resolveFrameAt rather than the resolver, so step 1 has its first consumer and the eventual split stays a packaging change. Nothing runs inside the webview: enableScripts is off and every name is escaped, because a column name is written by whoever wrote the data file.

impact high0.5 d

Expand and paginate shipped src/preview/table.ts · src/schema/rows.ts · polarsense.showData

A webview panel fed by parquetReadObjects({ file, columns, rowStart, rowEnd }), a hundred rows at a time, and parquet was the good case it promised to be: the read is bounded by the page whatever the file weighs, only the columns on screen are decoded, and the footer's row count gives the pager its end before a row is read. The panel that opens on a 5,000-column, 1.5 MB fixture opens on a four-million-row file the same way.

Where it differs from the plan is the word virtualised. A virtual scroller is a scrollbar that lies about its height plus a windowing calculation, and neither is needed to keep the promise underneath it — which is that nothing crosses the boundary that is not being drawn. Rows are paged a hundred at a time, and columns are a moving window of forty over the filtered list, stepped with ‹ columns and columns › and narrowed with the filter box. The sticky first column is the row index rather than the first data column, which turned out to be what actually keeps a wide table readable, and the header row is sticky too.

The formats degraded exactly in the predicted order. CSV is served out of the same bounded prefix the header read already takes: no row count to claim, no offset to seek to, the last record dropped because a read that stopped mid-line ends in half a row, and a note on the panel saying it is a prefix rather than the file. Arrow IPC, Delta and Iceberg say which half is missing — schema known, rows not read yet — rather than showing an empty grid that reads as an empty file.

The host owns every decision and the page owns none: the webview draws what it is sent and posts what was clicked, so no value from a data file is ever markup, and what to read is decided where it can be tested. The panel asks readRows on the exported API, which is step 1 earning its keep a second time.

impact high2 d

Show graph shipped src/schema/chart.ts · src/schema/series.ts · src/preview/graph.ts

Two separable halves, and the dependency the heading warned about never arrived.

Choosing the chart is the lookup table it was predicted to be, at about thirty lines and with the rows unchanged: one numeric column is a histogram, one categorical is a bar of counts, temporal against numeric is a line, numeric against numeric is a scatter, categorical against numeric is a bar of means — said on the axis as mean revenue, because a bar of means and a bar of totals look identical and answer different questions. Cardinality picks bars for a numeric column holding a dozen values or fewer, since thirty bins over five ratings is a comb rather than a distribution. Two things the plan did not have: a CSV has no dtypes at all, so where the file recorded none the family is read off the values themselves — a column that parses as numbers nine times in ten is numbers — and a pair given in the wrong order is swapped rather than refused, because nobody picks two columns in the order a lookup table happens to want them. The head of the list is the default and the whole list is the override, so a kind the picker does not offer is one these two columns cannot be drawn as.

Where the plan was wrong is the axis. The footer's min/max would set the range without reading a row — but by the time the range is wanted the column has already been read to bin it, so the range comes from the values and matches the bars exactly, which the footer's own statistics would not after a partial read.

Drawing it took no dependency: rects, a polyline and circles, built with createElementNS and textContent so a category out of someone's parquet file can only ever be a label. The bundle went from 264 KB to 285 KB — 20 KB, which is roughly what uPlot costs gzipped and a fraction of what Vega-Lite would have, with the difference that these twenty kilobytes draw four charts and nothing else. Five chart types became four — a bar of counts and a bar of means are one drawing routine with a different aggregate behind them — and the day's work was mostly axes, which is where hand-written SVG actually costs something.

What the plan understated is the read. A page formats a hundred rows for a grid; a bin count needs a whole column unformatted, so series.ts sits beside rows.ts as the widest read in the extension, bounded by graph.maxRows at 100,000 and saying a sample whenever it stopped short — a histogram of the first tenth of a file captioned as the file is the exact failure this project exists to avoid. The rule underneath held without effort: bin counts and category means cross the boundary, never rows, so a chart of a four-million-row file is the same thirty numbers as a chart of four hundred.

impact med2 d

The button under the cell output shipped src/renderer/index.ts · src/preview/buttons.ts · src/preview/cells.ts

A contributes.notebookRenderer for text/html, and the promise held: no kernel. The button posts the id of the output that was clicked and nothing else; the host takes the cell's last statement, hands the offset to resolveFrameAt, and opens the same two panels the palette opens. So the buttons work under an .ipynb that has never been run, on a frame defined eight cells earlier, because the assembler already reads a notebook as one module.

Three buttons was two until step 5 built the third; the bar carries Details, Data and Graph now, and the sentence below is why it did not on the day this shipped. A button that opens nothing is worse than no button, and the bar was one row of a table away from carrying it. The bigger difference is that the risk the plan flagged in a closing paragraph turned out to be most of the work: standing in for the built-in renderer means every HTML output in the notebook comes through this code — a plotly chart, a display(HTML(…)) banner — not only the frames. So the renderer draws the output the way the one it replaced draws it, script elements re-created so that outputs which draw themselves still do, and appends the bar beside that rather than instead of it. That drawing is one function, and it is what issue #153836 will land on the day VS Code offers a supported way to extend the built-in renderer instead of supplanting it.

What the plan did not foresee was the smallest question in it: which cell. VS Code hands the renderer an output id, but NotebookCellOutput does not carry one in the typed API, so the match back is against a field that is there at runtime and may not always be. When it misses, the focused cell answers — clicking inside an output is what focuses the cell holding it — and when that misses too, the panel says so rather than opening on whichever frame was nearest. Exact, then plausible, then nothing. And the takeover earned a setting: notebook.buttons turns the bar off, which leaves notebook output rendered exactly as it was before.

impact med1.5 d

Live frames from the kernel phase 2 · @vscode/jupyter-extension

The API is real and stable, and the sample is vscode-extension-samples/jupyter-kernel-execution-sample. Two constraints shape the design more than the API does. First, getKernel only returns kernels the user has already started, for notebooks that are currently open — so this is an enhancement to a session in progress, never a way to start one. Second, and worse: the frame has to be addressable. pl.scan_parquet(…).collect() as a cell's last expression has no name. IPython keeps it in _oh[n], which works and is how this can hook an unnamed output, but it is off when cache_size is zero and it pins the frame in memory. A named variable is the case to support properly; the unnamed one is a bonus that should fail quietly.

Everything else is easy once code can run: df.slice(off, n) is a page, df.describe() is the details panel, df.group_by(c).len() is the bar chart. Return write_json and parse it — never scrape the repr you were trying to escape.

The .py column is the one that decides the architecture, and it is the one that is easiest to skip past.

Read down the .py column. Path B answers no three times out of four, and the brief explicitly asks for .py as well as .ipynb. That is the case for building A first, stated more plainly than any argument about dependencies.

Part 04

One extension or two?

The question the brief asks last, and the one with the least obvious answer.

Not yet. Phase 1 belongs in PolarSense. Split at the moment you take the Jupyter dependency — and that moment is a real, nameable event, not a feeling.

The instinct to split is right about the destination and wrong about the timing. A second extension today means a second repository, a second release pipeline, a second marketplace listing, a second set of reviews, and an API surface between the two halves — all of it built before a single user has said the viewer is worth having. That is scaffolding for a building that has not been designed. The v1 roadmap made this call correctly twice already: cross-module frames became demand-driven rather than a workspace index, and cache warming got no state to go stale.

Phase 1 does not justify it either way. It adds a webview, a command and some SVG. It takes no new dependency, reads no rows it is not asked to read, and runs on the resolver that is already there. Inside PolarSense it is one src/preview/ folder and one entry in contributes.commands.

What makes the split correct, when it comes

The trust model, and nothing else. PolarSense's whole pitch is that it reads metadata and not your data — which is why values.enable is off by default and why its description says so in a sentence rather than a footnote. A viewer that reads rows on request is a stretch of that promise but still recognisably the same one: you asked for these rows, it read these rows. An extension that calls executeCode against your kernel is a different promise entirely, and it deserves its own marketplace page, its own permission conversation and its own one-star reviews. Bolting "also runs Python in your session" onto a completion provider is how a clean security story becomes an asterisk.

The secondary reasons are real but would not carry the decision alone: activation cost (a completion provider on onLanguage:python should not drag a charting bundle into every Python file, though a command-activated webview mostly avoids this anyway), extensionDependencies on ms-toolsai.jupyter, and a different marketplace category with Data Wrangler as the competitor rather than Pylance.

What to build now so the split is cheap later

One thing, and it costs an afternoon: make the resolver reachable from outside. Return an API object from activate() — resolveFrameAt(uri, position) giving path, schema and statistics — which is the ordinary VS Code mechanism for one extension to consume another and needs no package extraction, no monorepo and no versioning scheme. The viewer, whenever it becomes its own extension, declares extensionDependencies: ["Pinch.polarsense"] and calls it. Until then phase 1 calls the same function directly, in-process.

That resolver is the moat. Data Wrangler cannot tell you which parquet file is behind df without running your code; PolarSense can, statically, across module boundaries, before anything has executed. Both halves should be built on it, whichever VSIX they eventually ship in.

Things to get right early, because they are expensive later

Say what you are showing. Every panel header names the file, the row count and whether transforms were applied. The v1 habit of marking a sampled value (sampled) is the same habit and it is the one that keeps this trustworthy.

Never send rows you are not drawing. Pages and bin counts cross the webview boundary; datasets do not. This is the constraint that decides whether the viewer stays usable on a four-million-row file, and it is nearly impossible to retrofit once the message protocol assumes otherwise.

Reading rows stays opt-in in spirit. A preview panel is explicitly asked for, so it does not need a setting the way values.enable did — but it should never open by itself, never warm in the background, and never read on hover.

Not on this list

Editing. Data Wrangler's centre of gravity is generating cleaning code from UI operations, and that is a much larger product than a viewer — it needs an operation model, code generation per dialect, and undo. The brief asks to see the data. Seeing it well, for polars specifically, on files nothing else can locate statically, is a complete product on its own.
