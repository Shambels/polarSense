Roadmap · PolarSense 0.1.0

What PolarSense doesn't do yet

Everything the build plan scoped but v1 didn't ship, every limitation that was a deliberate trade rather than an oversight, and the features worth adding that weren't in the plan at all.

Effort figures are focused working days. Impact is my read on how many users would notice, not how interesting the work is.

Part 01

Planned, not built

Scoped in the build plan, cut to get a working extension out. Nothing here needs a design decision — the shape is already settled.

Object storage: s3:// and gs:// plan M6 · src/storage/

The one you said was real. Storage already abstracts stat/readAll/list/asyncBuffer, and hyparquet only ever asks for byte ranges — so S3 is GetObject with a Range header plus ListObjectsV2, and the credential chain comes free from @aws-sdk/client-s3. Needs ETag-keyed caching, a persistent globalStorage cache, and per-scheme opt-in so completions never issue billable calls unasked.

impact high2 d

Delta checkpoint fallback plan M5b · src/schema/delta.ts

The reader walks _delta_log/*.json backwards for a metaData action. A table whose JSON commits have been vacuumed leaves only *.checkpoint.parquet, and today that reports nothing at all. The fallback reads the checkpoint's metaData column through the hyparquet path already in the repo.

impact med0.5 d

Arrow IPC / Feather is a stub src/schema/parquet.ts

readIpcSchema returns an empty array with a comment explaining why. The schema is a flatbuffer at the head of the file; reading just the field names doesn't need a full Arrow implementation, but it does need a small hand-rolled flatbuffer walk.

impact low0.5 d

Release CI plan M9

Tag → run tests → vsce publish + ovsx publish. The fixtures are generated and gitignored, so the workflow has to install polars and run npm run fixtures before the reader tests can run — worth getting right once.

impact med0.5 d

Real editor integration tests plan M8

The current suite activates the bundled extension against a hand-written stub of the VS Code API — good enough to catch bundling and activation failures, which it did. It cannot catch anything about the real editor: whether quick suggestions actually fire inside strings, whether the replace range behaves against real auto-closing quotes. That needs @vscode/test-cli driving executeCompletionItemProvider in a real host.

impact med0.5 d

A demo GIF plan M9

The whole pitch is a two-second visual. Marketplace listings live or die on the first image, and there isn't one.

impact high1 h

Web extension build plan M9 · src/storage/local.ts

The plan said to keep the local reader on vscode.workspace.fs rather than node's fs so the extension would work in vscode.dev. It didn't — local.ts, paths.ts, parser.ts and notebook.ts all import node:*. The plan warned this is cheap at M1 and expensive to retrofit, and that turned out to be true.

impact low1 d
Part 02

Deliberate limitations worth revisiting

Traded away on purpose for a single-file, no-propagation v1. Each is asserted as a passing test, so fixing one is a visible change rather than a silent drift.

Schema propagation src/core/resolve.ts

The big one, and the source of every "why is it offering that?" report you will get. After df.select("a","b") the extension still offers all source columns; after .rename({"a":"z"}) it offers a and not z. The fix is architectural: resolve() returns a schema expression — a source plus a chain of transforms — instead of a bare SourceRef, and each of select / rename / drop / with_columns / join / group_by gets a small evaluator. Essentially a mini type checker for the polars API.

impact high3–4 d

Cross-module frames src/core/bindings.ts

A frame built in loaders.py and imported gets nothing, and with no escape hatch in v1 there is no workaround. Needs a workspace-wide index of exported frame-returning functions, kept current by a file watcher.

impact high2 d

The pragma escape hatch

Designed, then deliberately dropped. If frames from function parameters or config objects turn out to be common in your code, this is the cheapest correction — a comment the developer writes once, read by the existing resolver:

# polars-schema: data/sales.parquet
return pl.scan_parquet(cfg.source_path)
impact med0.5 d

df["…"] and get_column src/core/triggerSites.ts

You scoped these out of v1. Subscript access needs one branch in findArgumentPosition; get_column is literally one table row. The smallest useful thing on this whole page.

impact med1 h

Nested struct fields

.struct.field("…") completes nothing, because the readers flatten to top-level names. The parquet schema is already a tree — the flattening happens in readParquetSchema and would need to be preserved rather than discarded.

impact low1 d

Glob schema union, and hive dtypes

Two small honesty gaps. A multi-file glob reads the first match and assumes the rest agree; a heterogeneous set silently shows the wrong columns. And hive partition columns are always reported as str, where polars infers i64 for year=2026.

impact low0.5 d
Part 03

Not in the plan, worth adding

Ideas the build plan never considered, mostly because v1 was scoped to completion alone. Several are cheap because the resolver already does the hard part.

Complete the file path itself

Today pl.scan_parquet("da…") is classified not-a-column-site and offers nothing. But that string is a path, the extension already knows the workspace roots, and it knows which extensions each source function accepts. Offering matching data files there costs one branch in classifyCall and reuses everything else. Cheapest delight-per-hour on this page.

impact high0.5 d

Diagnostics for unknown columns

A squiggle on pl.col("regoin") — a typo caught while typing instead of at runtime, on a full scan, ten minutes in. The resolver already produces everything needed. The care required is in when to stay silent: only warn where the chain has no unmodelled transformation, or the limitations above turn into a stream of false positives, which is worse than no diagnostics at all.

impact high1 d

Hover with column statistics

Hover a column name, get its dtype — plus null count, min and max, which parquet already carries in the same footer the extension reads. No extra I/O for the common case; it's a display of bytes already in hand.

impact high1 d

Value completion

The showpiece. pl.col("region") == "…" offering EU, US, APAC — real values, read from the parquet dictionary pages of low-cardinality columns. Nobody's editor does this. It also crosses a line the extension has so far respected: it reads data, not just metadata, so it wants to be opt-in and documented plainly.

impact high2 d

Ctrl-click a path to open the file

A DocumentLinkProvider over the resolved path in pl.scan_parquet("…"). Two hours, and it makes the extension feel like it understands the project rather than just the strings.

impact med2 h

polars.selectors

cs.by_name("…"), cs.starts_with("…"), cs.ends_with("…") — a real and growing part of the polars API that the trigger table doesn't know about. Mostly new rows plus recognising the import polars.selectors as cs alias, which the import scanner nearly does already.

impact med0.5 d

Constraint keywords

df.filter(region="EU") — polars accepts column names as keyword arguments. This is the one completion on the page that fires outside a string literal, so it needs a different trigger path, but the schema lookup is unchanged.

impact med1 d

Columns inside SQL strings

df.sql("SELECT … FROM self") and pl.SQLContext are strings full of column names that no tooling understands. Needs a light SQL scan to work out which table a position refers to, then the same schema lookup.

impact low2 d

pandas, pyarrow, duckdb

The machinery is not polars-specific — pd.read_parquet("x.parquet") and duckdb.sql("SELECT * FROM 'x.parquet'") read the same footers. The trigger table is polars-shaped, but the resolver, readers, paths and cache are not. This is the largest audience increase per day of work available.

impact high1–2 d

NDJSON, JSON and Excel

scan_ndjson infers from the first line; read_json from the first object; read_excel needs a zip + XML read of the first sheet row. Each is small on its own.

impact low1 d

Warm the cache on open

Every source in a file is known the moment it's parsed, so the schemas could be read on open instead of on the first keystroke. That removes the one visibly slow moment in the whole product — the isIncomplete round trip — at the cost of some I/O nobody asked for.

impact med2 h

A "show schema" command

The status bar says 24 cols. Clicking it could show them — name, dtype, null count — in a quick pick that inserts the one you choose. Turns the existing status item from a debug affordance into a feature.

impact med1 d
Part 04

What I'd do next

Ordered — each one either unblocks the next or buys the most user-visible improvement per day spent.

  2. 2Path completion + ctrl-click to openUnder a day for both, they share the resolver, and together they make the extension feel like it understands the project.0.5 d
  3. 3Hover with statisticsFree data — it's already in the footer being read. Highest ratio of visible value to new code on the page.1 d
  4. 4Object storageBecause you said s3 is real for your work. Needs one decision first: profile, SSO, or a custom endpoint.2 d
  5. 5Schema propagationThe correctness ceiling for everything else. Diagnostics in particular are not safe to ship before this — false positives on transformed frames would poison them.3–4 d
  6. 6Diagnostics, then value completionDiagnostics once propagation makes them trustworthy. Value completion whenever you want the feature people screenshot.3 d
The ordering principle

Everything before item 5 is additive — new surfaces over a resolver that already works. Item 5 changes what the resolver returns, so anything built on top of it afterwards is cheaper than anything built on top of it now. That's the only real sequencing constraint on this page; the rest is preference.

One thing not on this list

Rewriting the analysis to use a real Python type checker's output — Pylance's or pyright's — instead of the hand-rolled binding table. It would solve cross-module frames and propagation at once. It is also a different product with a different failure mode, and pyright has no plugin interface for contributing string-literal completions. Worth knowing the door exists; not worth walking through it yet.
