Build plan · VS Code extension

Column names that come from the file, not from memory

A Python-language completion provider that reads the schema out of the parquet, CSV, Delta or Iceberg source behind a polars frame, and offers those column names wherever polars expects one.

01

The shape of it

Polars column names are strings. Every type checker in the Python ecosystem sees pl.col("revenue") as a string literal and stops there — polars #12673 and #18449 are the standing requests for exactly this, and neither has a shipped editor answer. The schema, though, is sitting in the file on disk: a parquet footer, a CSV header row, a Delta commit log, an Iceberg metadata JSON. All four are cheap to read and none of them requires running the user's code.

So the extension is a bridge with three spans: work out which file the frame under the cursor came from, read the schema out of that file, and decide whether this string position is a place polars wants a column name. Span one is the hard one — it's a small static analysis of Python. Spans two and three are bounded work.

Locked decisions

Why no Python subprocess

Worth restating because it shapes everything downstream: the extension never imports polars, never spawns an interpreter, and works in a repo you've just cloned with no venv. The price is that we reimplement polars' type display names and its path semantics, and we can be wrong about both. Object storage is the one place this could have forced a rethink — it doesn't, because the S3 and GCS clients hand back byte ranges just as well as a local file does, and hyparquet only ever asks for ranges.

03

Parsing

web-tree-sitter, not regex

The cursor is by definition in half-written code — pl.col("re with no closing quote. Tree-sitter's error recovery keeps producing a usable tree where a regex scanner or a strict parser gives up, and its incremental reparse keeps the per-keystroke cost at microseconds. Cost: two WASM assets, roughly 1.5 MB in the VSIX.

Why not reuse Pylance

No public schema hook

Pylance has no extension API for contributing string-literal completions, and its type engine has no notion of a parquet file. We register an independent CompletionItemProvider for language: python; the two coexist because they fire in different places — ours only inside string literals we've claimed.

04

Cursor → schema: the resolution algorithm

This is the component that decides whether the extension feels magic or broken. Written out as steps, running on every completion request:

  1. Anchor. From the cursor node, ascend to the enclosing string. If there isn't one, bail — we only ever complete inside string literals.
  2. Find the argument. Ascend past any enclosing list, tuple or dict until we hit an argument_list. Record the position (index, or keyword name, or "dict key"). If we hit a statement first, bail.
  3. Classify the call. Resolve the callee to a dotted name and look it up in the trigger-site table (§05). The table says whether this particular argument position takes a column name.
  4. Find the frame. If the call is a frame method, its receiver is the object it was called on. If it's a bare expression constructor like pl.col, walk outward through enclosing calls to the innermost frame method — this is what makes df.select(pl.col("…")) work.
  5. Reduce to a symbol. Walk left through the receiver chain — df.filter(x).group_by(y).agg collapses to df. A chain rooted directly in pl.read_parquet("…") skips the binding table entirely.
  6. Look up the binding. Nearest assignment to that name at or before the cursor, in the innermost enclosing scope that defines it.
  7. Fall back. No frame found — a bare expr = pl.col("…") at module level — offer the union of every schema bound in the file, each item labelled with its source file. Configurable, on by default; it's usually right and it degrades gracefully.
# the binding table after one pass over this file
df   = pl.scan_parquet("data/sales.parquet")      # SourceRef(parquet, "data/sales.parquet")
recent = df.filter(pl.col("date") > cutoff)       # alias → same SourceRef
joined = recent.join(dim, on="region")            # alias → recent's SourceRef
dim  = pl.read_csv(CSV_PATH)                      # const-eval CSV_PATH → SourceRef(csv, …)
mystery = make_frame()                            # unknown → no completions

# resolution walk for the cursor below:
#   string "re|"  →  arg 0 of pl.col  →  column site
#   no receiver   →  ascend to df.select(...)  →  receiver "df"
#   df            →  data/sales.parquet
df.select(pl.col("re|"))
Sharp edge · join

left_on= should complete from the receiver's schema and right_on= from the other frame's — which means resolving a second binding from the join call's first positional argument. Cheap enough to do in v1 and very visible when it's wrong, so it's scoped into M2 rather than deferred.

Notebooks: one module, assembled from cells

Notebook cells arrive at the provider as separate TextDocuments under the vscode-notebook-cell scheme, which would scope every binding to a single cell — useless, since the whole point of a notebook is that df is defined once at the top. The fix is to widen the binding pass rather than the parse:

  1. If the document's URI scheme is vscode-notebook-cell, find its parent through workspace.notebookDocuments.
  2. Take every code cell in document order up to and including the current one — document order, not execution order, because that's the order a reader assumes and the order re-running the notebook would use.
  3. Parse each cell separately (trees stay per-cell and per-version, so editing cell 8 doesn't reparse cells 1–7) and merge their binding tables in order, with later cells shadowing earlier ones.
  4. Resolve relative paths against the .ipynb file's own directory — the same default the Jupyter extension uses for the kernel's working directory.

Everything downstream — site matching, path resolution, readers, cache — is unchanged. The only new state is a per-notebook merged binding table, invalidated when any cell above the cursor changes.

06

Schema readers

One interface — read(uri, kwargs) → Promise<Column[]> where Column = { name, dtype, nullable } — and four implementations. Each maps its native types onto polars' display names (str, i64, f64, datetime[μs], list[str], decimal[18,2]) so the popup reads the way df.schema prints.

parquet

Footer only

hyparquet's parquetMetadataAsync over an AsyncBuffer: two range reads — the trailing 8 bytes for the footer length, then the footer itself. parquetSchema turns that into the schema tree; we flatten to top-level fields and map logical types (STRING, DECIMAL, DATE, TIMESTAMP with its unit) onto polars names. Milliseconds, regardless of file size.

csv

Header sniff, kwarg-aware

Read the first 256 KB, split on a real quote-aware scan, and honor the kwargs actually passed at the call site: separator, has_header, skip_rows, comment_prefix, new_columns, quote_char. has_header=False yields polars' generated column_1…column_n. Dtypes are omitted unless the optional row-sniff is enabled — a guess printed as fact is worse than a blank.

delta

Newest metaData wins

List _delta_log/*.json, read newest-first, scan each commit's newline-delimited actions for a metaData entry, parse its schemaString (Delta's own JSON schema), stop at the first hit. Covers every table whose log hasn't been truncated. When it has, fall back to _last_checkpoint → the checkpoint parquet, read through the same hyparquet path — that fallback is M5b, not blocking.

iceberg

Current schema off the pointer

metadata/version-hint.text names the current v{n}.metadata.json; without a hint, take the highest-versioned file. Read current-schema-id, find that entry in schemas[], map its fields[]. Filesystem tables only — REST, Glue and Nessie catalogs need a network client and are explicitly out.

Object storage without a Python fallback

The readers above never open a file. They ask a Storage abstraction for a byte range and for a directory listing — which is the whole reason s3:// stays compatible with the pure-TypeScript decision. Four implementations of two methods:

Rules for the remote path

Never prompt for credentials and never store any — if the ambient chain yields nothing, the source resolves to "unauthenticated" in the status bar and the completion is silently empty. Remote reads are opt-in per scheme (polarsColumns.remote.s3.enabled), because a completion provider that quietly issues billable API calls on every keystroke is a bad neighbour. Every remote read is coalesced, cached far more aggressively than local ones (§08), and capped at one in flight per URI.

Bundle cost: the modular AWS v3 client adds roughly 400 KB to the VSIX; the Google auth path is lighter. Both load lazily on first remote resolution, so a purely local user never pays the startup cost.

07

Paths and escape hatches

Between "the string in the call" and "a file on disk" sits a small constant evaluator, because real code rarely inlines a literal path.

  • Resolvable: string literals; f-strings whose parts are all literal; adjacent-literal concatenation; Path("a") / "b"; os.path.join(…); module-level string constants (recursively); str(…) wrappers.
  • Roots, in order: the directory of the .py file, then each workspace folder, then anything in the polarsColumns.pathRoots setting. First existing match wins — this is the fix for scripts that assume they're run from the repo root.
  • Globs and directories: data/*.parquet or a hive-partitioned tree reads the first match only, assuming uniform schemas. Directory segments shaped key=value are appended as hive partition columns, matching what polars actually hands back.
  • Absolute paths outside the workspace are used as-is; no root search, no sandbox complaints.
  • URIs — https://, s3://, gs:// — skip the root search entirely and go straight to the matching Storage implementation (§06). Globs over object storage become a prefix listing.

When the evaluator can't get there — the path comes from a config object, a function parameter, an environment variable — v1 does nothing. No pragma comment, no settings map: the frame resolves to nothing, the status bar says why, and no completions appear. This is a deliberate bet that literal-or-constant paths cover most real code; the two escape hatches stay designed but unbuilt behind the same resolver interface, so adding one later is an afternoon rather than a refactor.

08

Cache and latency

A completion provider that takes 200 ms feels broken even when it's correct. Two caches and one trick keep it under budget.

  • Schema cache — LRU, ~200 entries, keyed on uri + mtimeMs + size so a rewritten file invalidates itself. A FileSystemWatcher on resolved paths evicts on change; Delta and Iceberg watch their metadata directories and carry a 30-second TTL on top, since a table can gain a commit without any watched file changing.
  • Remote schema cache — same LRU, but keyed on the object's ETag instead of mtime, with a 5-minute TTL before revalidation and a persistent copy in the extension's globalStorage so reopening the workspace tomorrow doesn't re-fetch. A remote miss costs 100–400 ms, which is exactly what the isIncomplete path below exists for.
  • Binding cache — per document (or per notebook, merged across cells), keyed on document.version, rebuilt on change behind a short debounce. Rebuilding is a single tree walk; on a 2000-line file it's well under a millisecond.
  • Cold-read trick — if the schema isn't cached, don't block. Kick off the read, return an empty list with isIncomplete: true, and VS Code re-queries as the user keeps typing; by the second keystroke the items are there. Warm path stays fully synchronous after the cache hit.

Budget: p50 under 30 ms warm, p99 under 120 ms including a cold parquet footer read. A file with thousands of columns is the pathological case — cap the item list at a configurable 5000 and let VS Code's own filtering do the rest.

09

Completion UX

  • The items: label is the column name, detail is the dtype, kind is Field (the ◆ icon), documentation names the source file. sortText is a zero-padded schema-order index so columns list in file order rather than alphabetically, and range is set to the string's contents so replacing a partial name never eats the quotes.
  • Getting the popup to appear at all: VS Code suppresses quick suggestions inside strings by default. The extension ships contributes.configurationDefaults setting "[python]": {"editor.quickSuggestions": {"strings": "on"}}, plus " and ' as trigger characters so it also fires the moment a quote is typed. Without this the feature only works on an explicit Ctrl+Space — it is the single most likely reason a user reports "it does nothing".
  • Status feedback: a status-bar item, visible only in Python files, showing the resolved source for the frame at the cursor — or why there isn't one ("path not resolvable", "file not found", "unsupported scheme"). This is the debugging surface, and it costs a few dozen lines.
  • An output channel logging every resolution attempt at trace level. When someone files an issue, this is what you ask for.
10

What v1 gets wrong, on purpose

The single-file, no-propagation choice buys a large simplification and pays for it in specific, nameable ways. Better to document these in the README than to have them discovered:

  • Transformations don't apply. After df.select("a","b"), completions still offer all 24 source columns. After .rename({"a":"z"}), a is offered and z isn't. Schema propagation is the natural v2, and the architecture leaves room: the resolver would return a schema expression instead of a SourceRef.
  • Frames crossing module boundaries are invisible. A frame built in loaders.py and imported gets nothing, and with no escape hatch in v1 there is no workaround — the honest answer is "assign it from a literal path in the file you're editing".
  • Frames from function parameters or config objects are invisible. Type annotations carry no path, and we're not adding pragmas in v1.
  • Multi-file globs assume one schema. First match wins; a heterogeneous set silently shows the first file's columns.
  • The dtype names are our translation, not polars'. Edge cases — nested lists of structs, timezone-aware timestamps, large-string variants — will read slightly differently than print(df.schema).
  • Notebook order is document order. Cells run out of order get resolved as if they hadn't; a frame reassigned in a cell below the cursor but executed before it will be wrong. Matching the kernel's real execution history is possible but not worth it.

13

Testing

  • Resolver corpus. A directory of small .py files with | marking the cursor and an expected-source assertion beside each. Every row of the trigger table gets one, and every §10 limitation gets a case that asserts the current wrong-but-known behaviour, so a future fix is visibly a change.
  • Reader goldens. scripts/make_fixtures.py writes parquet, CSV, a Delta table with two commits, and an Iceberg table with a schema evolution, plus a JSON dump of each expected schema. The readers are asserted against those goldens — which also catches the day polars renames a dtype.
  • Integration. @vscode/test-cli driving executeCompletionItemProvider against real documents in a real editor host — the only way to catch the quick-suggestions-in-strings problem, which unit tests cannot see.
  • Perf guard. A 5000-column parquet and a 2000-line Python file, with an assertion on warm completion latency so a regression fails CI rather than the user's patience.
14

Packaging

  • esbuild to a single dist/extension.js; the two WASM files ship as assets and are loaded from the extension path at activation.
  • Activation on onLanguage:python only — nothing runs until a Python file opens.
  • Expected VSIX size around 2–2.5 MB: ~1.5 MB tree-sitter, ~400 KB AWS client, the rest ours. Storage clients are dynamic imports, so they cost nothing at startup.
  • Marketplace listing needs a publisher account, a 128px icon, a README opening with a demo GIF of the popup (record the §01 scenario), a licence, and a CHANGELOG.md. Publish to Open VSX in the same job — Cursor and Windsurf can't install from the Microsoft Marketplace, and that's a large slice of the polars audience.
  • Release CI: tag → build → vsce publish + ovsx publish, with the integration suite as a required gate.
  • State plainly in the README that the extension sends no telemetry and reads nothing beyond the byte ranges of the data files you point it at — worth saying up front given it holds cloud credentials in-process.
  • Extension host only, no language-server process — which also means it works in vscode.dev if the local reader is kept to the vscode.workspace.fs API rather than Node's fs. Worth doing from the start; it costs nothing at M1 and is expensive to retrofit.
15

Still open

Nothing blocks starting M0. Three things want an answer before the milestone that needs them:

  1. Which cloud, and how do you authenticate to it? (before M6) S3 with a named profile, S3 with SSO, GCS with ADC, or an S3-compatible endpoint like MinIO or R2 — each is a different line in the credential setup, and knowing which one is real means building and testing that one properly instead of all four shallowly.
  2. Is there a representative repo to test against? (before M2) The resolver corpus is only as good as the code it mimics. A handful of your actual polars files — how paths get built, how frames get passed around — is worth more than any number of invented cases.
  3. Extension name and publisher id. (before M9) Needed for the Marketplace listing; polars-column-sense or similar, under whatever publisher you register.

And one thing to watch rather than decide: if the no-escape-hatch bet turns out wrong — frames from function parameters are more common in your code than expected — the pragma comment is the cheapest correction and slots in behind the existing resolver interface.
